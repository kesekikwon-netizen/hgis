# 요청 기록: 파일 길이 검사를 커밋 전에 이 PC에서 하기

- 날짜: 2026-10-03
- 상태: 완료
- 관련 문서: docs/intent/2026-10-03-dev-setup-cleanup.md

## 요청 원문
> 이제 최고의 개발설정이 된건가?
> 추천진행 (Claude 추천: 파일 길이 검사를 커밋 전 검사 장치에 넣기)

## 문제
- GitHub 자동 검사의 「Source line limit」(src·tests의 C++ 파일은 300줄 이하, 이미 넘은 파일은 기준 파일에 적힌 줄 수보다 늘면 안 됨)는 GitHub에서만 돈다. 다른 대화들이 큰 파일을 늘린 커밋을 그대로 올려 10-03에 검사가 빨간불이 됐다.

## 바라는 결과
- 이 PC에서 커밋할 때, 커밋에 들어가는 C++ 파일이 300줄을 넘거나(기준 파일에 없는 경우) 기준 줄 수보다 늘면 커밋 전 검사 장치가 막고 이유와 고치는 방법을 알린다. GitHub와 같은 기준으로 센다.
- 기준 파일(docs/quality/line-limit-baseline.txt)에서 줄 수를 올리거나 파일을 새로 넣는 커밋은 메시지에 `길이 기준 변경: <이유>` 줄이 있어야 통과한다(시험 약화 막기와 같은 방식).

## 영향받는 곳
- 커밋 전 검사 장치(.claude/hooks/commit-gate.mjs)와 그 시험, Strata 작업 지침의 장치 설명 한 줄. 앱 기능은 바뀌지 않는다.

## 지켜야 할 것
- 세는 방법은 scripts/scorecard.ps1 -LineLimitOnly와 같게(src·tests의 .cpp·.h·.hpp, UTF-8 줄 수, 300줄).
- 장치가 고장 나면 지금처럼 막고 이유를 보인다(조용히 열리지 않게).
- 기술 선택(Claude가 정함): 커밋에 들어가는 파일만 센다(전체를 매번 세지 않음). 내용은 시험 약화 검사와 같은 규칙으로 고른다(평범한 커밋은 스테이징된 내용, -a·경로 지정은 작업 폴더).

## 이번에 하지 않는 것
- 이미 큰 파일을 쪼개기, GitHub 검사 바꾸기

## 미정 질문
- 없음(사용자가 추천 내용 그대로 「추천진행」).

## 확인 방법
- 시험 커밋으로 큰 파일을 늘리면 커밋 전에 막히고 「길이」 이유가 보인다.
- 기준 줄 수만 올리는 커밋은 「길이 기준 변경:」 줄이 있어야 통과한다.

## 결과
- 2026-10-03 완료. 커밋: d23b75f(검사 장치에 길이 검사), d34ec1c(코드 검토 지적 수정: 내용을 한 번에 읽기, 읽기 실패는 막기, 낮추거나 뺀 기준 확인, 시험 5개 더함). 기록 b7fca9a.
- 확인한 것: 장치 시험 26/26, 저장소 node 시험 101/101, 코드를 일부러 망가뜨린 15가지 모두 시험에 걸림. 실제 저장소에서 scorecard와 같은 셈(300줄 넘는 파일 91개, 문제 0건). 기준 파일에 있는 tests/test_layer_information.cpp 를 한 줄 늘린 시험 커밋은 「469줄, 기준 468줄보다 많다」로 막히고, 기준만 올리면 「길이 기준 변경:」 줄을 요구하고, 그 줄이 있으면 통과했다. C++ 파일 600개 커밋의 검사 시간 31.1초 → 0.8초(훅 제한 60초).
